03Opening

90 seconds. Say it in your own words; these are the points that must land.

Israr · opening SecureWallet is a mini fintech wallet: customers sign in, see their balance, send rupees to other customers and see their history, exactly the six operations in the brief. We didn't start from a list of security features. We followed the brief's chain, Asset → Weakness → Impact → Control: we listed what needs protecting, asked the brief's questions against our own design, found thirteen concrete weaknesses, and picked one control for each. Every control has a switch in our Security Lab, so we can show the attack working before and blocked after, and every one has an automated test. All 39 tests pass.

Stack

  • React 18 + Vite front end, served by nginx
  • FastAPI (Python 3.12) back end
  • PostgreSQL 16 database
  • Docker Compose, three containers

Numbers to remember

  • 13 weaknesses → 13 controls (W1–W13)
  • 39 automated tests, all passing
  • 6 defence layers (Lecture 2, L1–L6)
  • Money stored as integer paisa, never floats

04Architecture

Show the report's Figure 2 or draw this. The key sentence: the database itself enforces ownership, so a bug in the API cannot leak another customer's data.

Points to say

  • Two database roles. wallet_owner owns the tables; the API connects as wallet_app, which is not the owner and has NOBYPASSRLS, so every row-level-security policy applies to it.
  • The app role cannot change balances. It has no UPDATE on wallets and no INSERT on transactions; the only way money moves is the database function transfer_funds().
  • The database is unreachable from outside. It sits on an internal Docker network with no published port and no internet route.
  • Defence layers (Lecture 2): L1 trust the actor (passwords, tokens, PIN, passkey) · L2 validate the action (schemas, idempotency, risk) · L3 protect the data (RLS, encryption, atomic transfer) · L4 contain (Docker, CSP) · L5 detect (audit) · L6 recover (reconciliation).

password
Checked against an argon2id hash; never stored, never logged (the audit row has the username only).

          "iat": 1791802124, "nbf": 1791802124, "exp": 1791803024,
          "jti": "8bf94c74cc0f31ab1d2a29b5", "role": "customer", "name": "ali",

          "amr": ["pwd"], "sid": "a4769faa-…-3586f9c226e0"}
alg / kid
Algorithm pinned to ES256 (ECDSA P-256); kid picks the key. Blocks alg:none tricks.
sub
The user id. This is what RLS binds to the DB session. Changing it breaks the signature (W4).
aud / iss
Only this API accepts it; only our issuer signs it.
exp / nbf / iat
15-minute lifetime, 30 s clock leeway.
jti
Unique id; logout puts it on a revocation list so a copy dies immediately.
scope / role
What this user may do. Auditors get audit:read only, no transfer:write (W9).
sid
Server-side session id, checked on every request for the idle timeout (W13).
SayThe password is verified against an argon2id hash. We get back a short-lived signed token that stays in memory, and an HttpOnly cookie the page itself can't read. Notice the sid claim: the server tracks this session and will end it after five minutes of inactivity.

clientDataJSON
Written by the browser: type: webauthn.get, the challenge, and the real origin (http://localhost:8080). Server checks all three.
authenticatorData
37 bytes: rpIdHash (32) = SHA-256("localhost") · flags (1): UP=1 UV=1 · signCount (4), which must increase (clone detection).
signature
ECDSA P-256 over authenticatorData ‖ SHA-256(clientDataJSON), verified with the public key stored at registration. The private key never leaves the device.
SayA stolen password or session can't move this money. The server holds the transfer and sends a challenge that is a hash of this exact transfer. My device signs it after I verify with my fingerprint. The server recomputes the challenge from its own copy, checks the origin, the rpId hash, the user-verified flag and the counter, and verifies the ECDSA signature. Replaying the approval fails with 409 because it is single-use.

11Examiner questions

Short, confident answers. Click to open.

Why row-level security instead of just checking ownership in the code?
An ownership check has to be remembered on every endpoint; forgetting one is exactly how BOLA happens. RLS is enforced by PostgreSQL on every query from the app role, so a missing WHERE clause can't leak data. We kept the API filter too, as a second layer; the Lab shows that with the API filter off, RLS still returns 404.
Doesn't SECURITY DEFINER bypass RLS? Isn't that dangerous?
It runs as the table owner, which is why it can credit the receiver's wallet that RLS hides from the sender. To keep it safe it takes the sender from app_uid(), not from a parameter, re-validates the amount, and has a fixed search_path. It's the only path that can change a balance; the app role has no UPDATE on wallets.
Why argon2id and not SHA-256 or bcrypt?
SHA-256 is fast, so a leaked hash can be brute-forced quickly. argon2id is salted and memory-hard (64 MiB per guess), which makes GPU cracking expensive. It's the current OWASP recommendation; bcrypt is acceptable but not memory-hard.
Where is the token stored and why not localStorage?
The access token lives only in a JavaScript variable (lost on reload), so XSS can't read it from storage. The session survives reloads through an HttpOnly, SameSite=Strict refresh cookie that scripts can't read and other sites can't send. The CSP (script-src 'self') adds another barrier against XSS.
What stops someone replaying a captured passkey approval?
The challenge is random, single-use, bound to one pending transfer and expires after 5 minutes. A second confirm returns 409. The signature counter must also increase, which detects cloned authenticators.
How is a phishing site stopped by passkeys?
The browser writes the real origin into clientDataJSON and the authenticator scopes the key to the rpId (its hash is inside authenticatorData). A fake site has a different origin and rpId hash, so the server rejects it; the user has no secret to type into a fake page.
Why both a transaction PIN and a passkey?
Different risks. The PIN (W11) is on every transfer, so a session left open or a stolen token can't pay even small amounts. The passkey (W8) is the stronger, phishing-resistant factor for large or first-time-payee transfers. Layered: session → PIN → passkey above the limit.
Why aren't balances encrypted?
The database has to add them up, compare them and lock them inside transfer_funds() and reconcile_ledger(); encrypted numbers can't be summed in SQL. Balances are protected by RLS and least-privilege grants instead. We encrypt what doesn't need SQL arithmetic: names, notes, audit details.
What if the encryption key is stolen?
Then encrypted columns can be read; that's why the key lives in a separate volume, not in the database or the image. In production we'd use a KMS/HSM with envelope encryption and rotation; the v1 key id in every value supports that. We list this as a limitation.
What if the session cookie is stolen?
HttpOnly means page scripts can't read it, SameSite stops other sites using it, it rotates on every use with reuse detection that revokes the whole session, and the idle timeout limits how long it's useful. A copied cookie replayed directly would still work until one of those triggers; device binding (DPoP) is our planned fix. We were open about this in the report's limitations.
Is a 6-digit PIN strong enough?
Online, yes: three wrong entries lock transfers for 15 minutes, so guessing is impossible in practice. Offline, if the hashes were stolen, one million combinations is small even with argon2id, which is why the PIN is a second factor, never the only one.
How do you prevent double-spending with parallel requests?
Inside transfer_funds() both wallet rows are locked with SELECT … FOR UPDATE in a fixed order (by user id, so A→B and B→A can't deadlock), balances are re-read under the lock, then debit, credit and the transaction row are written in one database transaction. The W7 lab shows the lost update without locks, and reconciliation catches it.
How do you know the controls actually work?
39 automated end-to-end tests run against the Docker stack, each weakness tested before (control off, attack succeeds) and after (control on, attack blocked), plus the live Lab and the reconciliation report.
Isn't the Security Lab itself a vulnerability?
It only exists when DEMO_MODE=true. With the default false, the lab and trace endpoints aren't mounted at all (we tested this: 404), every toggle is audited, and Reset restores every control. Secure default.
Why 404 instead of 403 for another user's wallet?
A 403 would confirm that the wallet exists. 404 gives the same answer for “doesn't exist” and “not yours”, so ids can't be enumerated.

12Limitations (say them before they're asked)

  • No TLS locally. Browser↔nginx is HTTP on localhost (WebAuthn allows localhost). Production: TLS 1.3 at nginx.
  • Stolen session cookie analysed, not demonstrated; device binding (DPoP) planned.
  • Keys in a Docker volume, not a KMS/HSM.
  • In-memory IP limiter: needs Redis with several API instances (the account lockout is already in the DB).
  • Seeded money only: no bank top-up; that would need signed, replay-protected callbacks.
  • Simple risk rules: amount and new payee only; velocity and device signals are next.
